# Публикация структуры по техническому заданию

Актуальный источник требований — «КАТАЛОГ РАЗДЕЛЫ ТЭГИ(2).docx». Общий каталог сохраняет
`/instrukcii-po-ohrane-truda`. Два каталога, 52 раздела и 79 тегов получают самостоятельные страницы.
Для H01 используется предложенный в ТЗ `/po-professiyam/`, для H02 — `/po-vidam-rabot/`.
Предварительный список из 134 адресов находится в [instruction-taxonomy-urls.txt](instruction-taxonomy-urls.txt).
Окончательный перечень с учётом дополнительных элементов администратора формируется по runtime-реестру.

Публикация открывает страницы посетителям. Она не является командой на массовую индексацию.
Новые страницы остаются `noindex, follow`, включая пустые страницы и W21–W28. Уже опубликованные
элементы сохраняют редакторские SEO-поля и выбранную администратором настройку индексации.
Общий каталог сохраняет прежнюю доступность для индексации при первоначальной активации ROOT.
Теги с темами, пересекающимися с разделами, получают свои URL, но включаются в индекс отдельно
после проверки запросов и наполнения. SEO-тексты автоматически не генерируются.

## Предпросмотр

Передавайте CLI конкретный runtime-файл или его изолированную копию. Отсутствующий файл использует
исходный seed; родительский каталог должен существовать. Папка отчёта должна быть новой и находиться
вне каталога реестра. Пример на тестовой копии:

```bash
node server/scripts/publishInstructionTaxonomy.js \
  --file /private-staging/server/data/instruction-taxonomy.json \
  --output-dir /private-reports/publication-preview
```

Команда не запускает приложение, не читает инструкции и не меняет источник. Она создаёт:

- `publication.json` — проверяемый план с исходным и целевым состоянием, ревизией и SHA-256;
- `registry-before.json` — состояние реестра до изменения;
- `registry-after.json` — предполагаемое состояние для изолированной проверки;
- `urls.txt` — коды, постоянные адреса, статусы публикации и настройки индексации.

Сверьте изменения и адреса с текущим реестром. При конфликте кодов, родителей, адресов или
исторических редиректов CLI останавливается, не подбирая произвольное исправление. Дополнительные
элементы администратора сохраняются. Исторические опубликованные пути H01 и его разделов
получают редиректы к новым путям. Явный self-canonical старого пути на `https://boykovdocs.ru`
обновляется вместе с путём; внешний canonical не переписывается.

## Тестовая среда и резервная копия

До публикации на основном сайте выполните процедуру на отдельной актуальной копии трёх деревьев
данных и проверьте все публичные страницы через API и Nginx. Не изменяйте проверенную папку
`restored/`: для тестовой среды создайте отдельную рабочую копию. Секреты production и действующие
ключи платежей, почты и генерации в тестовое приложение не передавайте. У тестовой среды не должно
быть доступа к внешним сервисам; исходящие фоновые задачи должны оставаться изолированными.

Для переноса нужна свежая проверенная копия по [процедуре резервирования](instruction-taxonomy-rollout.md).
Старая копия до CSV-импорта не заменяет актуальный снимок после него. Дополнительно сохраните
текущие image ID, SHA кода, фронтенд, Compose и Nginx. Состав данных остаётся тем же:
`server/src/data`, `server/data`, `server/uploads`.

## Применение

Остановите API и остальные процессы, способные менять реестр. Затем примените проверенный план
к тому же состоянию реестра:

```bash
node server/scripts/publishInstructionTaxonomy.js \
  --file /private-staging/server/data/instruction-taxonomy.json \
  --apply-plan /private-reports/publication-preview/publication.json \
  --writers-stopped
```

Это пример тестовой среды, а не готовая команда для production. Для основного сервера после merge
фиксируются фактические SHA, образ, пути и проверяется свежий runtime-предпросмотр. Изменение
реестра выполняется атомарно под существующей блокировкой, с проверкой ревизии и всего исходного
состояния. Операция блокируется при незавершённом массовом изменении. При изменении реестра после
предпросмотра нужен новый план. Деплой исходников сам по себе ничего не публикует.

Команда изменяет только реестр. CSV повторно не применяется, назначения инструкций не меняются.
Подтверждённый импорт `e9e3a68b-34f5-4d7e-a3a0-0b9f56c6f15d` и его журнал остаются на месте.
Не заменяйте host mounts данными из Git или нового образа.

## Проверка после запуска

1. `/api/instruction-taxonomy/navigation` показывает 2 каталога, 52 раздела и 79 тегов исходной структуры.
2. Общий каталог содержит обычные HTML-ссылки на опубликованные страницы. Каталоги показывают
   все свои разделы. На инструкциях разделы, теги и промежуточные хлебные крошки ведут на эти страницы.
3. Все опубликованные страницы отвечают 200 и имеют собственный canonical. Пустые страницы и новые
   страницы без SEO-проверки имеют noindex и отсутствуют в sitemap.
4. На главной фильтры с параметрами получают `X-Robots-Tag: noindex, follow` от Nginx; без параметров
   запрет не добавляется. Для страниц каталогов сервер сохраняет прежние правила canonical/noindex.
5. В админке включение индексации наполненной страницы добавляет её в sitemap; выключение убирает.
   Снятие с публикации закрывает публичный адрес и удаляет его из навигации.
6. Проверьте поиск, алфавитную сортировку, сортировку по дате, пагинацию и мобильные ширины.
7. Откройте несколько действующих инструкций и скачайте PDF под тестовой учётной записью.

Для полного инвентаря и HTTP-отчёта используйте [инструкцию приёмки](instruction-taxonomy-acceptance.md)
с явным `--registry`, актуальным снимком инструкций и `--http-origin` тестового или основного сайта.
Модельный отчёт без HTTP-проверки не подтверждает фактическую выкладку. Ошибки и предупреждения
следует разбирать отдельно; 83 отложенные записи не должны исчезать из отчёта незаметно.

## Откат публикации

При остановленных писателях и неизменённом после применения реестре:

```bash
node server/scripts/publishInstructionTaxonomy.js \
  --file /private-staging/server/data/instruction-taxonomy.json \
  --rollback-plan /private-reports/publication-preview/publication.json \
  --writers-stopped
```

Откат возвращает содержимое реестра до активации с новой, увеличенной ревизией. Поздние изменения
администратора блокируют автоматический откат; они не перезаписываются. После отката для повторного
применения нужен новый предпросмотр. Файлы инструкций, их назначения, пользователи, платежи и
загрузки не восстанавливаются из старых копий. При откате релиза отдельно верните прежние код,
образ API, фронтенд и Nginx, сохраняя файл bind mount Nginx на месте.
